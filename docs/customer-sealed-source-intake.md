# Customer raw source intake

This source transport binds the literal Company.Name candidate at Customer base
`dd36b868f538d5d8f0d97cc20b3a676fc6ef3d01` to three exact Git blob objects in
`MALIEV-Co-Ltd/Legacy.Maliev.CustomerService`. Its separately sealed r4 policy
requires 275 raw files: 118 Customer sources, 141 frozen dependency sources and
16 validation inputs. The original candidate's six file seals and the complete
117 tracked-source inventory are checked before materialization.

The vendored decoder is the exact reviewed File module at protected File main
`53899c56ea3165e53ebbbcd60bff69a090037d9b`, SHA256
`44a8a5accac9da11422d606be02fe28487642215df511b5f1c4284296a453ee2`.
Both the decoder and caller policy are hashed before executing captured module
bytes or fetching blobs. Raw ZIP members, canonical headers, CRCs, complete
graphs, nested manifests and output bytes must match. Existing targets and
links are refused. No newline conversion or runtime source overlay is applied.

The hosted workflow has a five-minute lifetime, finite command deadlines and
read-only repository access. It runs intake controls, fetches only the three
prebound own-repository objects, materializes a fresh `/work/customer-source`,
then parses and runs the frozen provider's pure controls. It preserves the
actual receipt and logs and releases only its marked disposable directory.
It starts no SDK, PostgreSQL, Redis, Docker container or native test host.

Hosted pre-fetch checks select `test_customer_source_intake.IntakeControls`,
which use synthetic sealed fixtures. The separate `ActualPacketControls` class
was run locally against the retained immutable capsules and old r2 policy; its
off-repository evidence paths are intentionally unavailable in a Git checkout.
Hosted actual-packet qualification instead uses the fixed blob fetch and the
complete raw-graph checks during materialization, preserving the actual receipt.

The r4 provider source contains explicit owner-directed fixture disposal.
STOP and DELETE each refresh the exact receipt-bound target immediately before
mutation; deletion requires stopped state, no active execs, `force=false` and
`v=false`. GET inspection preserves an actual 404 only after a healthy exact
daemon and fresh full-ID inventory prove absence. Recovery retains its separate
SDK-first cleanup order. Ordinary fixture cleanup does not claim pooled-client
quiescence. The SDK's ledger mount is read-only; only the proxy writes receipts.

All 403 Customer cases remain a forecast (387 original plus 16 new). This
workflow's pure controls do not qualify application behavior, provider startup,
Docker HTTP101 transport or migration acceptance. The existing PR validation
continues to test the tracked baseline service independently; no candidate C#
source is installed into the tracked application by this PR.

Native candidate qualification still requires a specifically allocated finite
phase, fresh physical memory of at least 4,194,304 KiB at each phase, actual
predecessor handoffs, exact source/dependency/image/daemon pins and a reviewed
execution driver. Restore, strict Release build with zero warnings/errors,
focused regressions, full 403 cases and all four raw coverage floors remain
separate required checks. Source intake grants no native execution authority.

The raw capsule blobs are bound by object ID and SHA256 and read back before
publication is reported. They are not application source commits. If an object
becomes unavailable, intake fails closed and requires republishing the exact
bytes; it cannot fall back to a mutable ref or a different repository.
