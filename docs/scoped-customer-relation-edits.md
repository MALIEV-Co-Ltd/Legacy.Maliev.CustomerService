# Scoped company, billing and shipping editors

These commands restore the original Customer View's existing/new relation behavior without broadening profile PUT into arbitrary identifier assignment. Customer owns all three tables, so metadata creation and attachment occur atomically in this one database; Auth and other services are not part of that transaction. No identity email synchronization is performed.

All routes start `/customers/{customerId}/relations` and require existing `legacy-customer.customers.update`, resource `/customers/{customerId}`, in addition to the method's metadata permission. The customer editor already reads its ordinary profile to select the current relation identifier.

| Binding | Existing read | Existing save | Missing binding read/save | Additional permission |
|---|---|---|---|---|
| Company | `GET company/{companyId}/edit` | `PUT company/{companyId}/versioned` | `GET company/new`, `PUT company/new/versioned` | Existing read: companies.read; existing save: companies.update; new: companies.create |
| Billing | `GET billing/address/{addressId}/edit` | `PUT billing/address/{addressId}/versioned` | `GET billing/address/new`, `PUT billing/address/new/versioned` | Existing read: addresses.read; existing save: addresses.update; new: addresses.create |
| Shipping | `GET shipping/address/{addressId}/edit` | `PUT shipping/address/{addressId}/versioned` | `GET shipping/address/new`, `PUT shipping/address/new/versioned` | Same address permissions |

Metadata permissions have the unchanged `legacy-customer.` prefix and existing resources `/companies/{companyId}` or `/addresses/{addressId}`. Reads return only `CustomerId`, `RelationId`, and selected `Company` or `Address` safe DTO, with PascalCase/null omission, strong metadata ETag, X-Customer-ETag (the existing eight-hex-digit customer xmin validator), and no-store. Missing customer or mismatched binding returns404. New-binding reads require that the selected relation is absent.

Capture the metadata ETag and customer revision with the form. Send exact strong If-Match for the selected metadata and X-Customer-If-Match for the captured customer revision. Missing either428; malformed400; changed customer revision or selected metadata state412; mismatched relation binding404. Metadata validators bind customer ID, relation kind, actual FK and selected metadata state; customer xmin is compared separately under the same transaction lock. State validators are not ABA-proof revisions or durable replay receipts. Do not fetch a new token immediately before saving or replay uncertain writes.

A confirmed204 returns the selected metadata ETag, X-Customer-ETag for the committed customer revision, and X-Relation-Id for the actual saved metadata row (including a newly created ID). Carry only this confirmed customer revision into the next relation save or final profile conditional PUT, while retaining the originally captured metadata versions for untouched relations. This permits company/billing/shipping edits from one form without falsely rejecting the second operation due to its own first write. Other writers changing the profile between operations still produce412. When billing and shipping already share the exact address row, an address save also returns X-Billing-ETag and X-Shipping-ETag for that known committed shared-row edit; use only these confirmed counterpart versions for a deliberately following shared-address edit. Never replace an original validator for unrelated metadata with a freshly read value. There is no atomic transaction across separate commands, so later failures require explicit partial-outcome reporting.

Company body: Name, TaxNumber, Registrar. Address body: Building, AddressLine1, AddressLine2, City, State, PostalCode, CountryId. Unknown fields, including relation identifiers and timestamps, are rejected. Name/AddressLine1 remain required; CountryId zero is refused as in the original form's address-validity predicate. Company Name is persisted literally, without trimming, normalization or clipping. Its storage guard counts up to 256 UTF-16 units and rejects NUL/malformed UTF-16; supplementary characters consume two UTF-16 units and combining scalars separately. Scoped company Name remains nonblank and unknown fields remain forbidden. Address trimming/literal-null persistence semantics are retained. New-row routes create only when their missing-binding version still matches; no implicit replacement, arbitrary linking, detaching or cloning is added.

The repository locks the customer first and its currently bound metadata row second, re-reads the joined state, compares both the customer revision and selected metadata token, and verifies the requested binding. Creating metadata and setting only the selected FK commit in the same transaction. The customer's ModifiedDate/xmin rotates, preserving existing versioned-profile stale-edit protection. Other personal fields, private remark, relation IDs and Auth data are unchanged. Billing and shipping stay distinct bindings; when already sharing a metadata row, editing that row intentionally affects both and every other customer linked to it, as existing shared metadata semantics require. No automatic shipping-equals-billing reassignment is introduced.

Every retry begins with a fresh EF context; mapped xmin is explicitly selected by the customer locking query. After commit is attempted, failure or disposal uncertainty is fenced from retry rather than converted to stale412. Known or potentially committed mutations invalidate the exact linked customer caches with an independent token. Caller cancellation is preserved, including shared-cache cleanup; Redis outage can prevent cleanup and must not be mistaken for rollback. Normal profile reads remain database-authoritative. All ordinary profile/company/address routes and #197 revision behavior remain intact.

Component regressions use Production RS256 permissions, PostgreSQL18 and Redis, covering existing/new bindings, both customer and metadata authority, other-owner route rejection, profile and metadata staleness, missing/malformed tokens, mass-assignment refusal, shared cache scope, concurrent saves, postcommit uncertainty, captured-token sequential relation/profile saves, and known shared-address counterpart validators. The fixture uses broad signed permission fallback and does not demonstrate deployed IAM grants or resource-specific enforcement. This draft has not run build/tests/static/raw hosted gates and is not accepted. Root owns all Intranet consumer changes; no consumer, dependency, database model/migration, source history or tracking ledger changes are included.

Binding-move regression schedules cover company, billing and shipping individually. Before the customer fence, an ordinary profile PUT commits the move first and the delayed relation writer must return412 without changing any metadata. After the fence, pg_stat_activity must expose the ordinary writer waiting on a real PostgreSQL lock; only after the selected metadata commit can that writer move the binding. Every gate is released in finally; hosts and contexts are disposed. These authored cases remain unexecuted until hosted validation.
